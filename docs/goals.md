# Goals

A Goal is one objective that Paseo plans, carries out with several coding agents, reviews, tests and merges on its own branch. You start it once and read the result from the history. Goals are a fork addition; `docs/goal-orchestration-phase0.md` holds the reconnaissance and decisions behind the design.

## Roles

| Role     | What it is                                                                                                                                         |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Manager  | Daemon code, no model. Schedules tasks, records events, retries, enforces limits and recovers after a restart. `packages/server/src/server/goal/`. |
| Lead     | An agent that reads the repository and proposes the plan. It is also the conversation: the Manager messages it about failures and completion.      |
| Workers  | Agents that carry out tasks, each in its own worktree, on the task's provider or the goal's default.                                               |
| Reviewer | A fresh agent that reads one change and returns approve or request changes. It never wrote the change.                                             |
| Verifier | A fresh agent that checks each acceptance criterion against the merged result and gives evidence.                                                  |

Agents reason and edit. The Manager decides what runs, in what order, and what counts as done. The reducer (`goal-reducer.ts`) rejects any event that breaks the rules below, so a Manager bug cannot write an illegal state to the log.

## Start one

```bash
paseo goal create "Add rate limiting" \
  --objective "Limit the public API to 100 requests a minute per key" \
  --criterion "Requests over the limit get HTTP 429" \
  --criterion "Existing API tests still pass" \
  --cwd ~/code/api --lead claude --provider codex \
  --review-provider opencode --test-command "npm test" --auto-approve

paseo goal ls                     # --search, --status, --priority, --archived, --project
paseo goal inspect <id>           # tasks and their status
paseo goal changes <id>           # change sets and where each stands
paseo goal notifications <id>     # messages to the Lead and the chat, and their outcome
paseo goal inspect <id> --json    # full goal and event history
paseo goal reject-plan <id> --message "Split the migration out"
paseo goal pause <id>             # start no new worker runs
paseo goal resume <id>
paseo goal retry <id>             # retry failed tasks; reopens a failed goal
paseo goal config <id> --on-permission wait --max-runs 100   # change settings
paseo goal cancel <id>
paseo goal ack <id>               # dismiss an ended goal
paseo goal rename <id> "New title"
paseo goal priority <id> high     # low, normal or high
paseo goal archive <id>           # hide an ended goal from goal ls
paseo goal unarchive <id>
paseo goal delete <id> [--yes]    # remove an ended goal for good
```

`paseo goal ls` shows each goal's progress, elapsed time, reported usage and what it is waiting on. `paseo goal inspect` shows the same per task, and `paseo goal inspect <id> --usage` lists usage per agent, per role and in total.

Without `--cwd` the goal is manual: it records plans and state and nothing runs. With `--cwd` the Manager takes over. `--cwd` must be a git repository.

## Lifecycle

1. **Plan.** The Lead replies with a JSON task graph: ids, titles, descriptions, kinds (`implement`, `review`, `read`), dependencies, optional providers and optional `thinking`. The Manager checks it (no cycles, known providers, thinking ids the task's model lists, within the task limit, no ids ending in `-rw<n>`) and sends an unusable plan back, up to two times.
2. **Approve.** The goal waits for `paseo goal approve <id>`, or approves itself with `--auto-approve`. `paseo goal reject-plan <id> --message ...` sends the plan back instead: the Lead and its worktree are retired, and a new Lead plans with your feedback and the rejected plan in its prompt. A plan can be rejected 5 times.
3. **Execute.** Ready tasks start, at most `maxParallel` per goal and 4 across the daemon; when the daemon is full, a freed slot goes to the highest-priority goal with a ready task. Each task gets its own worktree. A task runs on its own provider or the goal's default. Its prompt includes the reports of the tasks it depends on. A failed task is retried after a backoff, up to `maxAttempts` failed attempts. A run interrupted by a restart does not count as a failed attempt.
4. **Capture.** When an implement task succeeds, its work is committed if needed and recorded as a change set with explicit base and head commits and the changed files. A task that changed nothing is recorded as such.
5. **Review.** A reviewer reads `git diff base..head` in the author's worktree. Changes it asks for, merge conflicts and test failures each become a rework task that continues in the author's worktree, up to `maxReworkRounds`.
6. **Integrate.** Approved change sets merge one at a time into the goal's integration branch in its own worktree. The branch is `<branchPrefix>/<goalId>`, `paseo-goal/<goalId>` by default, and Paseo's branch auto-namer is told to leave it alone. Its worktree path is in `paseo goal changes <id> --json`. `testCommand`, if set, runs after each merge; a failure resets the branch.
7. **Verify.** When everything is integrated, the verifier checks each acceptance criterion and records its evidence. Only then does the goal complete.

An implement task that depends on another starts only after that task's change set is integrated, and branches from the integrated commit, so it builds on the merged code.

The result is the integration branch and its worktree. Nothing is merged into your branch or pushed. Review it and merge it yourself.

## What is guaranteed

- **No unreviewed merge.** A change set can reach `integrating` only from `approved`, and `approved` only from a reviewer's verdict or your approval. The transition table in the reducer enforces it. Before each merge the pipeline also checks that the integration branch is where it left it, and resets it if something else moved it. Agents share the repository's git data, so a misbehaving agent could still try to write there; the checks catch that, they cannot stop it.
- **No early completion.** The reducer refuses `goal.completed` while a change set is neither integrated nor superseded, an implement task's work was never captured, or a criterion is unverified. A managed goal needs at least one criterion.
- **Your checkout is never touched.** Every agent, including the Lead, works in its own worktree. The integration branch is separate from your branches. Every worktree waits for its `paseo.json` setup to finish (up to 5 minutes) before an agent or a merge uses it. Worktrees start from the commit that was checked out in `cwd` when the goal was created, recorded as `baseCommit`, so a goal started on a feature branch builds on it.
- **Restarts lose nothing.** State is an append-only event log. After a restart, interrupted runs are closed out as interrupted and run again, and an interrupted run does not use up an attempt. A daemon that keeps crashing is bounded by `maxRuns`. A test restarts the daemon after each event of a full scenario and requires the goal to finish.
- **Every notification has a recorded outcome.** A message to the Lead (a task failed for good, the goal completed) or to the originating chat (how the goal ended) is recorded before it is sent, with its text, and each attempt is recorded as delivered or failed. A failed attempt is retried after 5 seconds, then 30, 120 and 300, five attempts in all; after the fifth failure the notification stays `failed` with its last error. Delivered means the agent layer accepted the prompt, not that anyone read it. After a goal has ended, only notifications, an acknowledgement, a rename, a priority change, a settings change, archiving and a retry that reopens it are accepted.
- **Duplicates do nothing.** An event id is recorded once. Resending a request with the same `eventId` returns the existing result. The CLI does not send an `eventId`.

## Control a running goal

- **Pause.** `paseo goal pause` stops new worker runs from starting. Runs already going finish and are recorded; their reviews, merges and rework scheduling continue. Nothing new starts, and the goal is neither verified nor failed for being stuck until you resume. Planning and plan approval still happen. Time, run and budget limits keep counting. The pause is an event, so it holds across restarts: interrupted runs are closed out and wait as pending tasks.
- **Retry.** `paseo goal retry <id> [--task <taskId>]` returns failed or cancelled tasks to pending. Their earlier failed runs stop counting against `maxAttempts`, so each gets a full set of attempts again; the run limit, time limit and budgets do not reset. On a live goal you can name one task. A failed goal is reopened to executing and every failed and cancelled task is retried, because one left behind would fail the goal again at once. A failed goal is not reopened when a change set was rejected (the goal can no longer complete), the run limit, deadline or a budget is used up, or nothing failed (a verification failure). Retry also waits until the failed goal's stopping agents have ended. After reopening, change sets are picked up where the failure left them, as after a restart, and the chat that started the goal is told about its next ending as well.
- **Reopen a planning failure.** A goal that failed before it had a plan (the Lead asked for a permission under `fail`, stopped, or gave no usable plan) has no tasks. `retry` on it, without `--task`, records `goal.reopened`: the goal goes back to planning with the same config, `reopens` goes up and the failure reason is cleared, and a fresh Lead plans in a new worktree, as at creation. The earlier Lead stays in the history as its own `lead.attached`. The run limit, time limit and budgets must leave room, as for any reopen. Change the setting that caused the failure first, for example `paseo goal config <id> --on-permission wait`.
- **Settings.** `paseo goal config <id>` (`goal.update_config`) changes a managed goal's settings in any state but archived: `onPermissionRequest`, `notifyLead`, `autoApprovePlan`, `requireHumanApproval`, `testCommand`, `maxParallel`, `maxAttempts`, `maxReworkRounds` and every `limits` field. The flags are those of `goal create`; `none` clears an optional one, so its default applies or the cap is removed. Providers, models, thinking, `cwd`, `branchPrefix`, `allowedProviders` and the objective are fixed; rename changes the title. Changes are checked as on create (ranges, a deadline in the future when it changed, `auto` against the role providers) and recorded as one `goal.config_updated` carrying the whole new config; the reducer refuses one that touches a fixed field. A live goal reads its settings at the moment it uses them: the next turn gets the new permission policy and run timeout, the next run its mode, the next launch the new `maxParallel`, run limit and budgets. The goal-time limit and deadline are re-armed at once. Turning on `autoApprovePlan` while a plan waits approves it; `requireHumanApproval` applies to reviews that finish afterwards. A limit lowered below what the goal has used is accepted, and the next check ends the goal as it would have at that limit: the next launch for runs and budgets, the re-armed timer for time. Raise a limit on a failed goal, then retry. The same settings again record nothing.
- **Cancel** is final. It is the stop: a live goal must be cancelled before it can be archived or deleted.
- **Rename and priority.** `goal.rename` and `goal.set_priority` work in any state, ended goals included, and record `goal.renamed` and `goal.priority_set`. A title is trimmed and must not be empty; there is no length limit, as on create. Priority is `low`, `normal` or `high`; a goal without one is `normal`, and `goal.create` takes it too. Priority does two things and no more: `goal.list` returns higher priority first (then oldest first), and when the 4 worker slots across the daemon are full, a freed slot goes to the highest-priority executing goal with a ready task, ties to the older goal. It does not pre-empt a running task, reserve slots, or change the Lead, reviews, merges, budgets or notifications, none of which wait for a slot. Setting the current title or priority again records nothing.
- **Archive.** `goal.archive` hides an ended goal from `goal.list` and sets `archivedAt`; `goal.unarchive` sets it back to null. A live goal is refused. An archived goal keeps its log, stays readable with `goal.inspect`, and can be acknowledged, but a failed one must be unarchived before a retry can reopen it. Archiving twice returns the goal unchanged.
- **Delete.** `goal.delete` removes an ended goal for good; a live goal is refused, and so is one whose agents are still stopping. The daemon does not ask for confirmation: the app and `paseo goal delete` do (the CLI needs `--yes` without a terminal or with `--json`). Deleting a goal that is already gone succeeds with `deleted: false`. See [Operations](#operations) for what is removed and what stays; the response lists what stays as `retained`.
- **Acknowledge.** `paseo goal ack <id>` (`goal.acknowledge`) dismisses an ended goal so it stops asking for attention. It records a `goal.acknowledged` event and sets `acknowledgedAt`, so the mark survives a restart. It changes nothing else: the status stays, and a failed goal can still be retried. A retry that reopens the goal clears the mark, so its next ending needs attention again. A live goal cannot be acknowledged; acknowledging twice returns the goal unchanged.

Gate each on its own `server_info.features` flag: `goalControls` for pause, resume, retry and plan rejection, `goalAcknowledge` for acknowledge, `goalBudgets` before sending `limits.maxTotalTokens`, `limits.maxCostUsd` or `limits.deadlineAt` (an older daemon drops them silently), `goalThinking` before sending any thinking field (the client refuses them without it, since an older daemon would drop them), `goalUpdates` for pushes, and `goalManagement` for rename, priority (on create too), archive, unarchive, delete and the `goal.list` filters, `goalConfigEdit` for settings changes, the `auto` policy (the client refuses it without the flag, since an older daemon's schema rejects it) and reopening a planning failure, and `goalUsageBreakdown` for usage per role and per agent. An older daemon ignores the filters and has nothing archived, so the client refuses filters without the flag. An older daemon also records nothing for a goal created without `onPermissionRequest`, which it runs as `fail`.

`describeGoalWaitingOn` in `packages/protocol/src/goal/waiting-on.ts` names what a live goal is waiting on (plan approval, a held change set, running tasks, review, merge, retry, verification, or a pause); the CLI and the app both use it. It returns an English `label` for the CLI and a translation `key` (`goals.waitingOn.*`) with `params` (`count`, `ids`, `title`, `tasks`) for the app. Use `count` for plural forms.

## Watching goals

`goal.list` returns every goal that is not archived, higher priority first, with its `usage` and a `progress` count (`tasksTotal`, `tasksDone`, `tasksFailed`, `tasksRunning`), enough for a list row without `goal.inspect`. `summarizeGoalProgress` in `packages/protocol/src/goal/progress.ts` computes the same counts for a daemon that predates `progress`.

The request takes optional filters, combined with AND: `query` (case-insensitive substring of the title, objective or id), `status` and `priority` (lists; a goal without a priority matches `normal`), `cwd` (the goal's `config.cwd`, compared exactly; manual goals have none) and `archived` (`exclude`, the default, `only` or `include`). `includeArchived: true` is shorthand for `archived: "include"`; `archived` wins when both are sent. A client that sends no filter, an older one included, gets every goal that is not archived. There is no pagination.

To be told about changes, subscribe to the `goal.update` session event (`session.events.set_subscription.request` with `events: ["goal.update"]`, or `observeGoalUpdates()` in the client). Each `goal.update` carries one goal in the shape `goal.list` returns. The first change to a goal is sent at once; changes in the next 250 ms are folded into one push of the latest state. Only connections that subscribed get it, and only with the `automation.manage` permission. Keep polling `goal.list` as well, at a slower rate: a push missed across a reconnect is not replayed. Archived goals are pushed like any other, so filter them out of a list that hides them. When a goal is deleted, one last `goal.update` carries its final state with `deleted: true`; drop it from your list. A change still waiting out its 250 ms window when the goal is deleted is not sent.

The reducer records when each stage started and ended, from the events alone, so replay gives the same times and older logs gain them too. A change set carries `reviewStartedAt` and `reviewedAt` (left `in_review` with a verdict), `mergeStartedAt` (first entered `integrating`) and `mergedAt`. The goal carries `verifyStartedAt`, the moment every task succeeded and every change set settled, and `verifiedAt`, when the last criterion was verified. Each is absent until its stage is reached.

## Usage and budgets

The Manager records one `usage.recorded` event per agent turn: Lead, workers, reviewers and the verifier. It holds what the provider reported for the turn, or nothing, plus a reviewer's `changeSetId` and the agent's `thinking`. The reducer adds each turn up four ways:

- `usage` on the goal: every turn (`inputTokens`, `cachedInputTokens`, `outputTokens`, `totalTokens`, `costUsd`, `reportedTurns`, `totalTurns`, `costReportedTurns`, `tokenReportedTurns`).
- `usage` on each worker run.
- `usageByRole`: the same totals per role, a role absent until one of its turns is recorded.
- `usageBreakdown`: one entry per agent with its role, task, run or change set, provider, model, thinking and totals. Retries and reworks start new agents, so they get their own entries. The provider and model come from the run, or from the role's provider in the goal's config, so older logs are broken down too. The breakdown keeps the 200 most recently active agents; `usageBreakdownTruncated` counts the ones dropped, which still count in `usage` and `usageByRole`.

Tokens mean the same for every provider:

- `inputTokens` is fresh input: tokens the model read that did not come from the prompt cache. Cache writes count here.
- `cachedInputTokens` is input read from the prompt cache. It is tracked and shown, and left out of `totalTokens`.
- `totalTokens` is `inputTokens` + `outputTokens`, the number `limits.maxTotalTokens` is checked against. Cache reads are left out because a long agent re-reads its context on every model call, so they would dwarf the work done, and they cost a fraction of fresh input.
- Every field covers the whole turn, subagents and every model call included.

Providers do not report this way, so the daemon converts at the boundary (`toTurnUsage` in `goal/goal-ports.ts`). Claude reports the process's running totals in `modelUsage` and `total_cost_usd`; its adapter reports each turn's share. Codex reports its last model call, with cache reads inside input; its adapter reports the turn's growth of the thread total. OpenCode, pi and omp report session totals; the goal takes their growth since the agent's previous turn. That baseline lives in memory, so after a daemon restart a resumed session's first turn counts the session so far. Other providers (ACP agents, Copilot) are taken as reported.

The conversion applies to turns recorded from v0.13.3 on. Older events keep the numbers they were written with and replay unchanged: Codex input there includes cache reads and covers only a turn's last model call, and a Claude agent's later turns repeat its earlier cost.

Treat the totals as a floor:

- Some turns report nothing, or report after the turn has ended (pi and omp poll session stats in the background). They count in `totalTurns` only.
- `costUsd` is what providers computed; Paseo never prices tokens itself. Codex reports no cost. When `costReportedTurns` is below `totalTurns`, the cost is a lower bound, and the CLI shows it as `>=$0.53`. Show the same next to any total: "cost reported for 1 of 4 turns". `tokenReportedTurns` does the same for tokens. Both are absent from older daemons.

`limits.maxTotalTokens` and `limits.maxCostUsd` fail the goal once the reported totals reach them, and a goal over budget is not reopened. They cannot stop a turn already running, and they never count what was not reported: a goal whose workers report no cost is held to `maxCostUsd` by its Lead and reviewers alone.

Gate the breakdown on `server_info.features.goalUsageBreakdown`. Clients without the `goal_usage_breakdown` capability get goals without `usageByRole`, `usageBreakdown` and `usageBreakdownTruncated`.

## Configuration

Set on `paseo goal create`; the fields listed under [Settings](#control-a-running-goal) can be changed later with `paseo goal config`. Defaults apply when a flag is omitted. Ranges and defaults live in `packages/protocol/src/goal/config-bounds.ts`, which the schema, the daemon, the CLI and the app share.

| Field                        | Flag                 | Default    | Meaning                                                                                                                                 |
| ---------------------------- | -------------------- | ---------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `cwd`                        | `--cwd`              | none       | Git repository the goal works on. The Manager runs the goal only when it is set; without it the goal is manual                          |
| `leadProvider`               | `--lead`             | required   | Provider for the Lead                                                                                                                   |
| `defaultProvider`            | `--provider`         | required   | Provider for tasks that name none                                                                                                       |
| `reviewProvider`             | `--review-provider`  | the Lead's | Provider for reviewers, and for the verifier unless `verifyProvider` is set                                                             |
| `verifyProvider`             | `--verify-provider`  | reviewer's | Provider for the verifier                                                                                                               |
| `leadThinking`               | `--lead-thinking`    | model's    | Thinking option for the Lead                                                                                                            |
| `workerThinking`             | `--worker-thinking`  | model's    | Thinking option for workers on `defaultProvider`. A task's own `thinking` wins                                                          |
| `reviewThinking`             | `--review-thinking`  | model's    | Thinking option for reviewers                                                                                                           |
| `verifyThinking`             | `--verify-thinking`  | model's    | Thinking option for the verifier                                                                                                        |
| `branchPrefix`               | `--branch-prefix`    | paseo-goal | Integration branch is `<branchPrefix>/<goalId>`. Segments of letters, digits, `.`, `_`, `-` joined by `/`, at most 100 characters       |
| `maxParallel`                | `--max-parallel`     | 2          | Tasks at once, 1 to 8                                                                                                                   |
| `maxAttempts`                | `--max-attempts`     | 2          | Tries per task, 1 to 5                                                                                                                  |
| `maxReworkRounds`            | `--max-rework`       | 2          | Rework rounds per change, 0 to 5                                                                                                        |
| `autoApprovePlan`            | `--auto-approve`     | off        | Run the plan without waiting for you                                                                                                    |
| `requireHumanApproval`       | `--require-approval` | off        | Hold every reviewed change until you approve it                                                                                         |
| `testCommand`                | `--test-command`     | none       | Shell command run in the integration worktree after each merge                                                                          |
| `notifyLead`                 | `--no-notify-lead`   | on         | Message the Lead about failures and completion                                                                                          |
| `onPermissionRequest`        | `--on-permission`    | `wait`     | `fail`, `wait` or `auto`. See [Security model](#security-model). Recorded at creation; a goal stored without it runs as `fail`          |
| `allowedProviders`           | `--allow-provider`   | any        | Restrict the goal to these providers                                                                                                    |
| `limits.maxTasks`            | `--max-tasks`        | 25         | Tasks in a plan                                                                                                                         |
| `limits.maxRuns`             | `--max-runs`         | 60         | Worker runs over the goal's life. Retries, rework and runs interrupted by a restart all count; Lead, reviewer and verifier turns do not |
| `limits.runTimeoutMinutes`   | `--run-timeout`      | 60         | Time for any one agent turn. The agent is then cancelled; if it has not stopped 30 seconds later, the turn is abandoned and fails       |
| `limits.goalTimeoutMinutes`  | `--goal-timeout`     | 1440       | Time from creation until the goal must be finished                                                                                      |
| `limits.retryBackoffSeconds` | `--retry-backoff`    | 5          | Pause before a retry, times the attempt number                                                                                          |
| `limits.deadlineAt`          | `--deadline`         | none       | ISO time the goal must be finished by. Must be in the future at creation; the earlier of this and `goalTimeoutMinutes` applies          |
| `limits.maxTotalTokens`      | `--max-tokens`       | none       | Reported fresh input plus output tokens over the goal's life, 1000 to 10 billion. See [Usage and budgets](#usage-and-budgets)           |
| `limits.maxCostUsd`          | `--max-cost`         | none       | Reported cost in USD over the goal's life, 0.01 to 100000; turns without a reported cost add nothing                                    |

Every provider field, and a task's `provider` in a plan, takes `<provider>/<model>`, so each role (Lead, workers, reviewer, verifier) can run its own provider and model (`--lead codex/<model>`) as well as a bare provider id. The daemon splits at the first `/`; a bare id starts the provider's default model. `allowedProviders` lists bare provider ids and is matched against the part before the `/`.

A thinking field holds a thinking option id from the model's catalog (`thinkingOptions[].id`), the same id a chat passes as `thinking`. Unset leaves the model's default. Roles do not inherit each other's thinking, unlike providers: an id belongs to one model, and the roles may run on different ones. For the same reason `workerThinking` applies only to a worker whose provider value is exactly `defaultProvider`; a task on another provider uses its own `thinking` or the model's default. A rework task keeps the original task's `thinking`. Each worker run records the thinking its agent started with as `thinking` (on `run.attached` and the run): the id asked for, or the provider's default when the provider reports one. The Lead, reviewers and the verifier have no run; read their setting from the config. `goalRoleThinking` in `packages/protocol/src/goal/thinking.ts` resolves a role's thinking for display.

Creation fails at once if a provider is not registered, is outside the allow-list, `cwd` is not a git repository, or a thinking id is not one the role's model lists. When the provider's catalog cannot be read, or does not list the model, the id is accepted and the provider decides when the agent starts.

When a limit is reached the goal fails, its agents are cancelled, and the reason is recorded. `paseo goal approve-changeset` and `paseo goal request-changes --message ...` act on changes held by `--require-approval`.

## Security model

Goals run with the `automation.manage` permission, the same as schedules. Anyone who holds it can start agents that run commands on the machine. The boundaries below limit what a goal does by accident, not what a malicious holder of the permission can do.

- **The permission policy sets the agents' mode.** Every agent works in a worktree. Under `wait`, the default, agents start in the provider's default mode and a permission request stays pending in Paseo for you to answer; the run timeout ends one nobody answers (the turn is abandoned even if the provider ignores the cancel). Under `auto`, agents start in the provider's mode with id `auto` (Claude's Auto mode, which a classifier approves; Codex's `auto`, its default approval flow) and anything still asked waits as under `wait`. Goal creation and `goal config` refuse `auto` when a role provider's mode list has no `auto`, as Claude's has none on Bedrock or Vertex; a provider whose modes cannot be read, or a task's own provider from the plan, starts in its default mode instead. Under `fail`, agents start in the provider's unattended mode (Claude's bypass), act without asking, and a run that still asks fails. `goalPermissionPolicy` in `packages/protocol/src/goal/config-bounds.ts` resolves a stored config: a goal created before `wait` became the default stored nothing and keeps running as `fail`. A new policy applies to agents created after the change; agents already running keep their mode.
- **Read-only roles are checked, not trusted.** The Lead plans in a worktree of its own, kept while the goal runs and archived if it is cancelled or fails. A reviewer that changes the change it reviews has the changes undone and its verdict discarded. A verifier that leaves the integration branch changed or dirty has its verdict discarded and the branch reset.
- **`testCommand` is a shell command you chose.** It runs with your privileges in the integration worktree and has a fixed 10 minute limit. It is judged by its own exit, so a background process it leaves behind does not fail it, and it is killed when the goal ends or the daemon shuts down. Agent-written code runs inside it, so use a command and repository you trust.
- **Agent text is data.** Findings, test output, task reports and errors that reach another agent's prompt are quoted between delimiters that change on every prompt. That lowers the risk of prompt injection and does not remove it. An agent that reads attacker-controlled files can still be steered.
- **Plans cannot widen the goal.** A plan that names a provider outside the registered set or the allow-list is sent back. Task ids ending in `-rw<n>` are reserved. A managed goal's plan can only come from its Lead; `goal.propose_plan` is refused for it.
- **Verdicts are judgments.** A reviewer or verifier records evidence, and it can be wrong. For anything that must not depend on an agent's word, put it in `testCommand`.

Not protected: network access, files outside the worktrees that the agents' mode lets them reach, and credentials in your environment. Treat a goal like a script you let a contractor write and run.

## Operations

- **State.** One file per goal, `$PASEO_HOME/goals/<goalId>.jsonl`, one event per line, fsynced on append, and the directory is fsynced when a new log is created. A torn last line from a crash is truncated on load. Do not edit these files.
- **Delete.** A deleted goal's log is first renamed to `<goalId>.jsonl.deleted` (one atomic rename, then a directory fsync), so after a crash the goal is either whole or gone. Next its timers are dropped and every worktree it recorded (the Lead's, the integration worktree, each change set's and each run's) is archived through Paseo, which removes the directory of a Paseo-owned worktree that no other workspace uses. A worktree with uncommitted changes is kept. Branches are never deleted: the integration branch holds the goal's result and the change set branches its history. Last the tombstone is removed. A start that finds a tombstone finishes the deletion. The goal id can be used again afterwards.
- **Unreadable logs.** A log that fails to replay, or comes from a newer version, makes that goal unavailable and is logged at start. Other goals and the daemon are unaffected. The file is left as it is.
- **Compatibility.** There is no migration step. Event changes are additive, and tests replay logs written by each earlier phase. An implement task that succeeded before work capture existed cannot be recovered; its goal fails rather than completing unreviewed.
- **Worktrees.** The worktree of a failed run is archived when it fails, not after its retry backoff. Worktrees of abandoned runs, and of read and review tasks, are archived too. Worktrees of successful implement tasks, the integration worktree and the Lead's worktree are kept so you can inspect them. The Lead's worktree is archived if the goal is cancelled or fails. Archive the rest from Paseo when you are done, or delete the goal.
- **Restarts.** A graceful shutdown stops the Manager before agents close, so runs are not recorded as failures. The next start marks them interrupted and runs them again with a new run id. It also sends every notification still pending at once, for ended goals too, within the five attempts; a delivered one is never sent again. Goals from before notifications were recorded have none and are not messaged again.
- **Cancel.** `paseo goal cancel` stops the Lead, workers, reviewers and verifier, the test command and any retry backoff, and archives the worktrees of every run still in flight. Uncommitted work in those worktrees is lost.
- **Concurrency.** At most 4 worker runs across all goals, and `maxParallel` per goal. The Lead, reviews, merges and verification are not counted. A task waiting out a retry backoff holds no slot. When a run ends, executing goals are offered the freed slot in priority order, then oldest first. Priority only orders that hand-off: a goal that becomes ready while a slot is already free takes it, whatever its priority.
- **Logs.** The Manager logs under the `goal-manager` and `change-set-pipeline` modules in `daemon.log`.

## Supported workflows

- Feature or fix work on a git repository that decomposes into tasks, with a test command that can judge a merge.
- Mixed providers: a planner on one, implementers on others, an independent reviewer on a third.
- Unattended runs bounded by time and run limits, and runs gated by your approval of the plan, each change, or both.

Not supported: goals without a git repository, merging into your branch or opening a pull request, re-planning around a failed criterion (the goal fails), and multi-repository goals.

### In the app

- **List.** Goals waiting on you come first: a plan or a change set held for approval, or a failure. Filters narrow to Needs you, Running or Done, and to one project once the goals span more than one. Each row names the goal's project and directory, says what the goal waits on, and shows the host's `progress` counts and its usage (against the cap when one is set). A total that only some turns reported is prefixed `≥`, and a host that counts cost reports and got none says cost is not reported; this is the rule `paseo goal ls` prints as `>=$0.53` and `no cost`. With no goals, the screen offers templates that fill the create form.
- **Search, priority, sort, archived.** Search matches the title, objective, id and project name. It runs in the app on the full list, not through `goal.list`'s `query`: the list is never paged, and the host does not know project names. With `goalManagement`, a priority filter and Show archived appear; Show archived fetches `archived: "include"` under its own query key and lists archived goals in their own group, muted. The sort (priority, recently updated, newest, name) orders goals inside each group and is remembered per device (`goal-list-preferences-store.ts`). An archived goal never needs you, so it leaves Needs you and the badge.
- **Manage.** Each row has a kebab (hover-revealed on web, always shown on touch and compact layouts), and the detail header has the same menu, built by `goalAvailableActions` in `packages/app/src/goals/goal-management.ts` from the goal's state and the host's flags: Rename, Priority, Edit settings, Pause or Resume, Retry, Dismiss, Archive or Unarchive, Cancel goal, Delete. Archive and Delete appear only on ended goals; cancel a live one first. Retry is hidden on an archived goal. Cancel and Delete ask first; Delete says branches are kept and, when the host retained anything, lists it in a toast. Priority changes show at once and roll back if the host refuses. A `goal.update` with `deleted: true` drops the goal from every cached list.
- **Needs you.** On hosts with `goalUpdates`, `useGoalUpdates` applies each `goal.update` to the cached `goal.list`, so the badge and toasts react at once; polling drops to every 60 seconds to repair a push missed across a reconnect. Other hosts are polled: `GoalAttentionWatcher` every 15 seconds, the Goals screen every 5. A push older than the cached goal (lower `lastSeq`) is dropped, and a poll never overwrites a newer pushed goal. The sidebar badge counts plans and change sets held for approval, not failures. A goal that starts waiting shows a toast naming what it waits on; the first list after launch stays quiet.
- **Dismiss.** With `goalAcknowledge`, an ended goal's detail offers Dismiss, and so does a failed goal's list row. A dismissed failure leaves Needs you but stays under All and Done, marked Dismissed. A retry clears the mark.
- **Detail.** The stepper, the banner and the progress panel all derive from the goal state in `packages/app/src/goals/`, with the phase taken from `describeGoalWaitingOn`. A Team section lists each role's provider value and thinking from the config (`goalTeam`); each task row shows the thinking its latest run started with (`AgentRun.thinking`). Held change sets get Approve and Request changes. Each task opens the agent of its latest run. Pause, Resume, Send back (plan rejection) and Retry appear only with `goalControls`. A goal that failed before it had a plan offers Retry planning instead, and only with `goalConfigEdit` too, since an older daemon refuses that retry. When the failure was a permission request (`needs_permission`), the detail says to pick Ask me or Auto mode in the settings first; retrying unchanged fails the same way. The activity feed shows settings changes and planning restarts. Waiting-on text is translated from the `goals.waitingOn.*` key and params; the protocol's English label is only the fallback. Locales whose plural rules need more forms than one and other (Russian, Arabic) list them next to a base key, which `TranslationResources` allows for `goals.waitingOn`.
- **Edit settings.** With `goalConfigEdit`, the detail header and the row menu open a sheet with the settings `goal.update_config` takes, for any goal but an archived or manual one. It sends only the fields you changed. While it is open, a config pushed by the host updates the fields you have not touched and keeps the ones you have. The sheet says the new values apply from the next turn or run, and that an agent already running keeps its mode.
- **Progress is an estimate.** The percent weights each implement task as half done when its run succeeds, three quarters when its change is approved, done when merged; planning and verification bracket the tasks. Time left needs two finished tasks and spreads the fastest and slowest over `maxParallel` (at most 4), then adds the review, merge and verification still ahead, sized from the stage times this goal already recorded. On a host without stage times, or before a stage has finished once, that stage adds nothing, so read the range as a floor. Task bars show each change set's review and merge windows, and verification gets its own bar.
- **Usage.** A Usage section under the progress panel holds tokens and cost for the whole goal, with the cap bars. Tokens are input plus output; input, cache reads and output are listed under the total, using the meanings in [Usage and budgets](#usage-and-budgets). A total that only some turns reported reads "At least" with "cost reported for 1 of 4 turns" under it; none reported reads "Not reported", never `$0.00`. Token counts use the CLI's one-decimal format so the two can be compared. With `goalUsageBreakdown`, By role and By agent fold out: one line per role and per agent, newest first, named by task title or run or change set id, with provider, model and thinking, and "Older agents not shown" when the host dropped some. Wide layouts align the numbers in columns; compact ones fold them under the title. An older host gets the totals and a line asking to update it.
- **Project.** A managed goal starts by picking a project: the host's git projects, most recently used first, or another folder (the desktop folder dialog when the host is this computer's daemon, a typed path otherwise). The form picks for you in this order: the directory it was opened from (the chat, or the workspace you were in, kept exactly, so a worktree's branch is what the goal builds on), your last project on that host, the host's most recently used project. The form asks the host for the folder's checkout status (`checkout_status_request`), refuses one that is not under git, and shows the branch the goal will build from. It cannot show the base commit: the status carries no head commit. A goal's project is named by matching its `cwd` against the host's project roots and workspace directories; a folder the host does not list shows under its own name. With more than one connected host that runs goals, the form also picks the host; a goal started from a chat stays on the chat's host so the outcome can be posted back.
- **Create form.** The objective is the only text you must write when the goal is manual; the title defaults to its first line. Careful, Balanced and Turbo fill every advanced setting; Balanced is the daemon's defaults. Number fields take typed values with units (`90m`, `1.5h`, `250k`, `$12.50`) or a horizontal drag on their handle; on web, arrow keys step and Shift steps further. Only the handle takes the drag, so the form still scrolls vertically on touch. Ranges come from `GOAL_CONFIG_BOUNDS`: a value outside one shows an error and is clamped when the field loses focus. An empty budget means no limit. The permission choice is Ask me (the default, `wait`), Auto mode (`auto`, shown only with `goalConfigEdit` because an older daemon's schema rejects it) and End the run (`fail`); a refusal from the host shows in the form. The form remembers your last managed goal per host (project, providers, settings) and offers its settings as Mine; it never overrides the directory the form was opened with; the test command comes back only for the same directory. The budget inputs appear only on hosts with `goalBudgets`, since an older daemon would drop the caps silently. With `goalThinking`, each role's model picker is followed by a Thinking picker filled from that model's `thinkingOptions` (no model means the provider's default model, as the daemon picks it); it is hidden when the model offers none. The reviewer and the verifier run on the review provider, or the Lead's when none is chosen, so their pickers follow that model. Changing a provider or model drops a level the new model does not list. Model default sends nothing. Presets leave thinking alone; the remembered last goal carries it. Optional fields equal to the daemon's default are left out of the config, except `onPermissionRequest`, which is always sent: an older daemon would run a goal without it as `fail`. The form memory is at version 2, which reads a remembered `fail` as `wait`, because `fail` used to be the form's default and was stored whether or not you chose it; if you did choose it, choose it again. The form does not set per-task providers or thinking, `verifyProvider`, `branchPrefix` or `limits.deadlineAt`.

### From a chat

In an agent chat, `/goal <objective>` or **Start goal from this chat** in the tab's menu opens the create form with the goal run by agents, the chat's working directory, and the chat's provider for the Lead and tasks. Without text after `/goal`, the objective is the chat's last message. The goal gets its own Lead; the chat stays as it is and receives the outcome, because the form sets `originAgentId` to the chat.

## Known limits

- Setup scripts run in every goal worktree. Anything setup leaves uncommitted in the integration worktree is reset before the first merge; setup output in a task's worktree is committed with its work and goes through review.
- The reviewer check sees `HEAD` and uncommitted files in the author's worktree, not ignored files or other refs. Reviewers legitimately run tests that create ignored files, and every agent shares the repository's refs, so a ref snapshot would flag other agents' own commits; neither check is done.
- A reviewer or verifier interrupted by a restart is not cancelled before its replacement starts. If a provider keeps agent processes alive across a daemon restart, two could briefly work on one worktree.
- Verification runs once, after all changes are integrated.
- A crash after a merge commit but before it is recorded leaves that commit on the integration branch; recovery resets the branch and merges again.
- If `cwd` is a subdirectory of the repository, git commands run in that subdirectory of each worktree.
- Quoting agent text in prompts does not stop prompt injection.
- A notification is sent at least once, not exactly once. If the daemon stops after the agent layer accepted it but before that was recorded, the next start sends it again. A crash after a goal ends but before its notifications are recorded loses them.

## Changing goals

- Add fields and event types; never change or remove the meaning of an existing one. Old logs must still replay, and the compat test must cover the change.
- Put every rule the Manager relies on in the reducer. The Manager can then be wrong without corrupting a goal.
- Use commits, not branch names, for anything stored. Paseo can rename a worktree's branch.
- Keep new RPCs under the `goal.*` namespace and gated on `server_info.features.goals`, or on the flag added with them.
- A new event type breaks an older client's strict event union. `goal-session.ts` leaves such types out of `goal.inspect` for clients without the matching capability (`goal_control_events` covers `goal.paused`, `goal.resumed`, `goal.retried` and `usage.recorded`; `goal_acknowledge_events` covers `goal.acknowledged`; `goal_management_events` covers `goal.renamed`, `goal.priority_set`, `goal.archived` and `goal.unarchived`; `goal_config_edit` covers `goal.config_updated` and `goal.reopened`, and without it an `auto` policy is sent as `wait`, in `goal.list`, `goal.inspect`, mutation responses and `goal.update` pushes; without `goal_usage_breakdown` the same payloads leave out the usage breakdown); add yours there.
- A new push message must reach only clients that asked for it. Deliver it as a session event subscription, as `goal.update` is, and return false for it in `legacyWantsEvent` in `session.ts`.
